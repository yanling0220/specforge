## 1. 填写实际目标

使用用户指定的专用测试项目和飞书群。先填写下表，再生成实际待办预览；预览核对完成后，针对该项目、群、成员和消息集合取得真实发送授权。

| 项目 | 当前值 / 要求 |
|---|---|
| 测试仓库路径、稳定 projectId | 可使用上述隔离项目，ID 为 im-acceptance；如需其他项目，再提供路径和 ID |
| 专用群及逻辑 route.id / revision | 待提供；管理员确认群成员可阅读该项目 |
| 成员映射 | 待提供；项目内有效 dev / product 用户 → 对应群成员 Open ID，分别明确谁被 @ |
| Webhook / 签名密钥环境变量名 | 待提供；值留在服务进程环境，不放入 JSON、命令行参数或验收记录 |
| publicBaseUrl、部署模式及前缀 | 待提供；成员能访问的 HTTPS 地址，路径与 server --base-path 一致 |
| 本人登录 | 对应成员持有各自项目登录令牌，令牌通过既有安全渠道分发 |
| 真实发送授权 | 待实际预览后记录；指定目标与两项通知，不扩大到其他项目或群 |

[关闭配置模板](examples/notifications.acceptance.json) 的用户名、Open ID、项目 ID 和地址均为示例。复制到本机部署目录后替换成已核对的实际值，保持 `enabled: false`。模板可解析不代表真实映射、凭据或地址可用；`.invalid` 地址不能用于验收。环境变量必须在启动 server 的进程中生效。

本次只在隔离目录准备演示状态和离线预览，没有启动连接真实渠道的通知服务；默认测试仍使用隔离夹具和注入传输。

## 2. 准备两项可观察待办

在该专用测试项目通过现有 CLI / Web 和引擎准备两项待办；先保持通知关闭：

1. **问题确认**：一条已有答案、最新修订 pending 的问题。由 dev 起草，已自动确认 dev，只缺 product；配置的 product 测试成员为有效接收人。
2. **开发签字**：另一条 closing 变更。引擎实时检查该档位上游门禁、G6A 以及绑定当前 HEAD 的 agent-review 均通过，当前 SHA 没有 human 审查记录；配置的 dev 测试成员为有效接收人。

验证证据通过 `sf verify` 在干净 worktree 中实际采集；使用已存在的独立审查记录或经授权的审查流程。真实模型调用仍需用户同意。不能直接修改阶段、伪造通过记录或复制浏览器测试中的注入证据来制造真实就绪状态。业务写入通过现有引擎 / Store.mutate 完成。

**首次启用会扫描整个项目。`notify preview/status --change` 仅过滤命令输出，不能限制 worker 的发送范围。** 因此下面的最终预览必须省略 change 筛选，并且只出现这两项新待办。若该项目已有其他待办或历史 queued / retry_wait，先选用隔离的专用测试项目，不通过删事件或索引清空记录。

在目标项目 Git 工作目录执行（下列 `/opt` 与 `/srv` 为部署路径示例）：

```bash
rtk node /opt/specforge/apps/cli/src/main.ts log verify
rtk node /opt/specforge/apps/cli/src/main.ts notify preview --notifications /srv/specforge/notifications.acceptance.json --project im-acceptance
rtk node /opt/specforge/apps/cli/src/main.ts notify status --notifications /srv/specforge/notifications.acceptance.json --project im-acceptance
```

多项目 preview 增加 `--multi-project`；project 参数替换成实际 ID。期望 `enabled: false`、`configuration: ready`、`pendingCount: 2`、`eligibleAfterEnableCount: 2`，两条候选 `existing: false`、`status: queued`、`attempts: 0`、`recipientStatus: ready`；status 中无历史发送记录。缺少凭据时应显示 configuration blocked，不能把该结果视为可发送。

预览必须保留两条实际通知编号、对象版本 / SHA、mentions 和 links，核对全部接收人。两类消息由生产模板渲染，以下只是结构示例，不能替代实际预览：

```text
SpecForge · <项目别名>
<change> / <Q> 第 <rev> 版（<答案短哈希>）待 product 确认
通知 n-<编号> · <观察时间>
@<配置的 product 测试成员>
打开平台核对当前状态 → <HTTPS 基址>/#/changes/<change>/analysis/<Q>

SpecForge · <项目别名>
<change> / commit <当前 SHA 前 12 位> 待 dev 签字
通知 n-<编号> · <观察时间>
@<配置的 dev 测试成员>
打开平台核对当前状态 → <HTTPS 基址>/#/changes/<change>
```

多项目在基址后增加 `/p/<projectId>`；基址包含已核对的部署前缀。消息不应出现问题 / 答案正文、代码、验证输出、内部路径或凭据。

先用关闭配置启动服务并通过实际 HTTPS 地址检查登录页面和深链接可达，构建与前缀按 [通知说明](im-notifications.md) 配置。preview / status / 页面 GET 均不应增加通知事件；登录只建立会话，不确认问题或签字。保存此时的业务事件序号与 HEAD，随后停止服务，复核实际全项目预览。

## 3. 核对预览后执行真实发送

将实际群、成员、两条完整预览及发送范围交给用户核对；确认授权后才启用。范围为两项逻辑通知。生产 worker 对明确限流会自动退避，每项每轮最多 5 次请求，初始两项合计最多 10 次请求；unknown、blocked 或 failed 停止对应通知，额外人工重试另行核对。测试过程中不新增答案修订、改变 HEAD、修改成员 / 路由或产生其他待办。

1. 把本机已核对配置改为 `enabled: true`，用相同项目、模式和前缀启动生产服务。例如单项目在其 Git 工作目录运行：

   ```bash
   rtk node /opt/specforge/apps/server/src/main.ts --notifications /srv/specforge/notifications.acceptance.json --base-path /console/test
   ```

   多项目增加 `--projects /srv/specforge/projects.json`，通知配置只启用该测试项目。启动前保存的配置、凭据和映射必须与预览一致。

2. 用 status 观察账本。在没有限流的正常路径上，两条分别为 accepted、attempts=1。记录实际 UTC 时间、通知编号、分类结果与群消息数量。accepted 只证明接口受理；由对应成员在群中确认实际出现且 @ 指向本人，分别记录两类结果。出现未知 / 失败结果时正常关闭服务，保留现场，按运维文档处理；本次不自动人工重试。
3. **暂不确认问题或签字**，保持两项需求有效。先等至少 15 秒（覆盖多个 5 秒扫描周期），核对群内仍只有这两条消息，status 的 key / accepted / attempts 未变。
4. 正常关闭，保持相同仓库、HEAD、稳定 ID 和配置重启，再等至少 15 秒。核对同一组 accepted 记录、累计 attempts 和群内消息数量仍未变。两次检查均记录观察起止时间；保留源事件与发送账本。

静态需求下重复扫描和重启不增加群消息，是本轮真实去重证据。先把需求处理完再等待，不能单独证明 accepted 去重。

## 4. 从收到的消息完成本人操作

1. product 测试成员用未登录的浏览器打开群内问题链接，登录该项目后仍定位到同一问题；查看当前答案，由本人点击确认。记录当前 rev / answerHash、成功事件序号、actor 的 product 角色以及没有 recordedBy 的结果。打开链接和登录本身不应增加业务事件。
2. dev 测试成员从群内签字链接进入对应 closing 变更，登录该项目、复核当前材料后签字；记录 human 审查的 reviewer、完整 SHA 和事件序号，SHA 应与通知及操作时 HEAD 一致。产品身份无签字权的自动化回归沿用 d 的证据，不为 e 增加新消息或伪装其他成员。
3. 等待后再次查看 status 和全项目 preview：两项当前需求已结束，原 accepted 历史与 attempts 保持，群内没有新增提醒。
4. 正常关闭服务，恢复本机配置 `enabled: false`。需要保留 Web 服务时用关闭配置重启。停止新请求后再保存最终发送账本、业务事件和 `sf log verify` 结果。
