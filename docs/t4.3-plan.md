# T4.3：单服务器多项目与可选 Postgres

状态：T4.3a 范围草案，待用户确认；本文描述的是待实现能力，不代表多项目或 Postgres 已经可用。任务状态只记录在 [TASKS.md](TASKS.md)。

## 1. 已确认的方向

- 一台服务器保存多个 Git 项目，小团队通过同一服务的网页入口协作，不做开发者电脑上的远程执行端。
- 每个项目的 `.specforge/`、OpenSpec 文件和 Git 历史继续作为项目事实来源；引擎守门、采集证据和写入事件的规则不变。
- Postgres 先作为可重建的查询索引，不将项目状态迁成数据库权威，也不设计文件与数据库的双重权威。
- 分步验收，每完成一个子任务先报告整体状态、验证结果和后续选项，由用户决定是否继续或推送。

## 2. 建议的首版边界（待确认）

| 事项 | 建议 | 取舍 |
|---|---|---|

## 3. 设计约束

### 3.1 项目隔离

- 多项目模式必须由显式登记的项目 ID 解析仓库，不接受客户端直接传文件系统路径。登记时校验真实路径、Git 根目录和 `.specforge/config.json`；拒绝别名重复、符号链接绕过及共享 Git 元数据的重复接入。项目 ID 在索引生命周期中保持稳定，不可悄悄换绑另一个仓库。
- REST、WebSocket、身份、索引、门禁评估、证据和定时锚定都绑定项目上下文。相同的 change ID、Q 编号和事件序号可以同时存在于不同项目。
- 项目状态、用户名册、事件链及 Git 审计分支各自独立；给索引和传输封装附加项目 ID，不修改已有事件的被哈希内容。
- 一个项目不可用时，对该项目明确报错并拒绝写入；不得误用其他项目作为默认值，其他健康项目仍可使用。

### 3.2 身份与网页

- 多项目模式仅接入已启用用户名册的项目；未启用用户名册的旧单项目本机只读模式保留，不据此放开团队访问。
- 项目会话必须绑定项目 ID，并隔离 Cookie 的路径或名称；不能仅凭同名用户、相同角色或传入的 project ID 跨项目授权。令牌不能出现在 URL、日志或项目配置中。
- 项目选择、登录和登出不能泄露未授权项目的业务内容；普通问题深链接在登录后仍指向原项目、原问题。
- 切换项目时重置角色、请求缓存、操作表单和 WebSocket 重连游标，防止旧项目的数据或写请求落到新项目。已经打开的 WebSocket 在账号停用或令牌重置后不得继续接收业务数据。
- 项目管理员仍只管理本项目名册；服务端项目登记权与网页里的 dev / product 角色分开。非本机部署继续要求 HTTPS 反向代理。

### 3.3 文件写入与并发

- 锁以仓库为粒度，而非 change 为粒度，因为用户名册和所有 change 共用一个事件序列与链头。不同项目无需共用一把写锁。
- 锁覆盖完整的读取、校验、文件写入和事件追加周期；`Store.mutate`、用户名册修改、创建 change、证据保存、独立事件追加和人工确认带外修改都必须参与同一机制。不得只锁 HTTP 或绕过现有引擎入口。
- 锁争用应等待到明确超时或拒绝本次操作，不能覆盖别人刚写入的状态；超时 / 失败不生成成功事件。需要多进程测试，不能只用同一进程里的 Promise 模拟。
- 进程中断、锁清理和文件写到一半的恢复边界必须明确：不能把多文件写入称为数据库事务，也不能自动确认带外修改来掩盖中断；无法证明一致性时拒绝后续写入，并给出人工恢复指引。
- 会改 Git 工作区的长任务也不能与同仓库的其他冲突任务并发；此阶段不引入分布式调度或宣称已有恶意代码沙箱隔离。

### 3.4 Postgres 与迁移

- 先抽出查询索引接口，再实现 SQLite / Postgres 两个后端；调用端兼容异步查询，不能以同步 SQLite 的调用方式假装支持网络数据库。
- 共享索引中的 change、question、event 均以项目 ID 限定查询与唯一性，例如 `(project_id, change_id)`、`(project_id, change_id, question_id)` 和 `(project_id, seq)`。分页游标和重建进度也按项目独立。
- 切换索引后端时，从各项目权威文件全量重建，再持续增量同步；不依赖旧 SQLite 文件、不重写旧事件、不改变现有哈希链与可信 Git 锚定。提供 schema 版本和升级说明。
- 保留项目级事务更新索引和原有日志重算 / 截断检测，重建一个项目不能清空其他项目的数据。索引丢失可重建，但不意味着源文件被删除或审计链异常可以忽略。
- 未配置 Postgres 时不连接数据库。连接信息只从指定环境变量读取，配置保存变量名，不记录密码或完整连接串。
- 显式选择 Postgres 后，连接、schema 或同步失败必须报告不可用 / 滞后状态，不能默默回退到空索引或把陈旧列表当作最新事实；不得通过重新执行已成功的文件写操作来修复索引。索引状态不能决定门禁通过。
- 回退 SQLite 只需更换索引配置并从文件重建，不涉及权威状态反向迁移；Postgres 是索引，不替代仓库、证据和独立审计锚定的备份。

## 4. 验收标准

以下是实施完成后的验收要求，当前均未验证。

| 编号 | 可观察的验收结果 |
|---|---|
| T43-AC-01 | 一台服务接入 A、B 两个独立仓库，均含同名 change / Q 编号及相同事件序号；详情、筛选、分页、证据、门禁、事件链和锚定互不串用 |
| T43-AC-02 | A 的会话不能读取、修改或订阅 B；伪造项目 ID / 角色不越权；停用账号、重置令牌后，旧 HTTP 会话及已连 WebSocket 不能继续访问该项目 |
| T43-AC-03 | 路径穿越、未登记项目、重复真实仓库及符号链接别名被拒绝；未经授权不泄露仓库路径、项目业务名称或统计；一个项目损坏不影响其他项目 |
| T43-AC-04 | 两个真实进程并发修改同一项目（含不同 change、用户名册或追加事件）时，无丢失修改、重复序号或链分叉；锁超时无成功事件，不同仓库不被全局串行阻塞 |
| T43-AC-05 | 中断写入与进程退出的故障用例有明确结果和恢复指引；状态不一致时拒绝写入，不能自动补成功记录或自动确认带外修改 |
| T43-AC-06 | 浏览器能按入口切换 A / B 并保留问题深链接；角色、表单、缓存和断线游标不串项目；T4.2 旧答案引用仍被拒绝 |
| T43-AC-07 | SQLite 与真实 Postgres 上的索引契约测试得到一致的过滤 / 分页结果；首次同步、增量同步、日志截断与单项目重建不污染其他项目 |
| T43-AC-08 | SQLite → Postgres → SQLite 重建前后，源文件、事件哈希和 Git 锚定不变；断库、schema / 同步失败不展示伪造成功、不自动重放业务写入 |
| T43-AC-09 | 未配置 Postgres 仍能运行原单项目 CLI / server；旧链接和身份规则兼容；配置及日志无密钥泄露 |
| T43-AC-10 | 全量 typecheck、测试、Web 构建及多项目浏览器端到端通过；新增用例之外原有 218 个测试仍通过，并记录真实 Postgres 验证环境和结果 |

## 6. 本轮需用户验收的选择

建议接受第 2 节的首版边界，下一轮只做 T4.3b。最重要的取舍是：首版账号仍按项目独立，而非一次登录所有项目。

如果必须一次登录访问多个项目，应先修改本方案，补充中心身份、项目成员关系、历史用户名映射和权限审计迁移，再开始 T4.3b；优点是使用方便，代价是明显扩大身份模型及兼容性改造范围。
