# T4.5：IM 通知范围与验收方案

状态：2026-11-17 更新；用户于 2026-11-16 确认飞书专用项目群机器人方案。T4.5a～d 的实现与测试已交付，整体 verify，e 待开始；已交付判定、发送账本、飞书适配器、后台 worker、本机管理入口与部署前缀，使用注入传输和真实 Chrome 验收，尚未发送真实消息。任务状态与实测证据以 [TASKS.md](TASKS.md) 为准。

## 1. 目标与建议范围

人在平台外收到“现在需要你处理”的提醒，打开链接后在对应项目登录、查看最新材料并操作。首版只覆盖两类提醒：**已有答案待角色确认**、**收尾检查通过后待开发者签字**。

首版已选用飞书，每个项目配置一个专用群机器人，按缺少的角色提醒显式配置的成员；默认关闭，管理员配置并启用后才发送。本文描述整个 T4.5 的目标；当前实现见第 8～10 节，管理命令、重试预算和部署前缀的完整用法见 [通知说明](im-notifications.md)。

| 选择 | 优点 | 代价 / 限制 |
|---|---|---|
| 专用群机器人（已选定） | 部署简单，团队能看到谁在等待处理；无需先建设统一账号或 IM 应用授权 | 群内其他成员也看得到消息，无法保证仅被 @ 的人可见；群成员权限需管理员维护 |
| 应用机器人私信 | 收件人明确，适合项目之间不能共享群可见性的场景 | 需应用权限、令牌管理及平台用户绑定，部署和实测更复杂；若选择此项，先调整 b/c 的接入设计 |

首版只实现飞书一种渠道。T4.5c 接入时核对其官方发送、签名、@ 成员、限流与错误码契约。

用户已确认渠道与群方式、下面的触发口径，以及默认不外发业务正文的内容范围。具体项目 ID、群与成员、环境变量和外部访问地址在部署时配置；真实测试消息需在 T4.5e 指定目标并另行授权。

## 2. 触发口径

### 2.1 已有答案待确认

由引擎读取当前问题状态，满足以下全部条件才有通知需求：

- change 尚未 `delivered`；问题为 `drafted`，最新答案修订为 `pending`。
- 用 core 的 `currentRevision`、`isResolved`、`missingRoles` 计算；按缺少的 `dev` / `product` 角色各生成一项通知，不按“所有未解决问题”发消息。
- 问题可出现在任意未交付阶段，包含 agent 后续回流的问题。`question.answered`、`question.role_required` 等事件用于唤醒重算，事件名称本身不证明需要发送。

回答者的角色可能已自动确认，不能再催同一角色。其他同角色成员中任一人合法确认后，这个角色的需求就结束，不要求该角色所有人逐个确认；保留当前引擎的按角色确认规则。

| 当前变化 | 通知结果 |
|---|---|
| 只有 open 问题，还没有答案；最新答案被驳回 | 不发“待确认”；待回答不在首版范围 |
| 开发起草第 1 版，已自动确认 dev，还缺 product | 只提醒配置的 product 成员 |
| 同文再次起草第 2 版 | 按第 2 版创建新需求，旧版尚未发出的通知取消 |
| 原已确认答案追加 product 角色，回到 drafted | 即使修订号未变，也产生 product 角色的通知需求 |
| 已确认、推迟、作废、角色不再缺少或 change 已交付 | 取消尚未发送的对应通知，不再重试；已发送消息不撤回 |

不通知 `agent` 角色，也不因通知需要而追加角色、改答案、代录确认或修改问题状态。

### 2.2 待开发者签字

采用“材料已就绪，再请人签字”的口径。引擎在同一个仓库锁快照内确认：

1. 当前阶段是 `closing`，获得当前 HEAD 的完整 SHA。
2. 用 `evaluateAll` 实时评估，`upstreamGates('closing', tier)` 对应的门禁全部 `passed`，G6A 为 `passed`。
3. G6B 中 `agent-review` 检查已通过且绑定当前 SHA；复用 `evaluateReview`，不能只看存在一条 verdict=pass 的记录。
4. 当前 SHA 没有 human 审查记录。当前 SHA 最新 human 记录为 pass 表示已签字，为 fail 表示已经打回 / 需修复，两种情况都不催签。

接收角色只有 `dev`，产品角色和管理员身份本身不获得签字权。不同 SHA 是不同通知需求；旧 SHA 的签字不覆盖新 SHA。进入 delivered、打回 implement、HEAD 改变、上游或验证 / 审查失效后，旧通知在发送前重新校验并取消。若同一 SHA 的就绪条件恢复，未成功发送、非 unknown 且未因失败 / 配置暂停的同一通知可重新进入待发，沿用原键和剩余尝试预算；已成功通知不再自动催办。

“升级给人”本身不触发签字提醒；升级后人完成修复，在新 SHA 上重新满足上述条件时可以通知。这里的就绪判定只控制提醒时机，不增加或改变现有签字权限、签字接口与门禁规则。

## 3. 接收人、项目与内容边界

- **逐项目配置**：沿用稳定 projectId 与已校验的仓库绑定。多项目使用登记 ID，单项目启用通知也需指定稳定 ID。A / B 的同名账号、change、Q 编号、SHA 和事件序号不能共用通知键、路由或成员映射。换绑仓库 / 改项目 ID 要有显式迁移，不静默重置去重记录。
- **显式成员映射**：管理员将项目用户名映射到所选 IM 的成员标识，并列出该项目允许接收提醒的用户名。每次发送前，将该列表与当前完整性校验通过的用户名册、未停用账号及缺少角色取交集；不根据同名、邮箱猜测身份，也不向所有名册用户自动发送。角色有多个配置成员时，一条角色通知 @ 这些成员；双角色分别去重。
- **缺少映射**：没有有效接收人、成员标识不受所选渠道支持、路由或凭据缺失时标为 blocked 并向管理员显示原因，不退回全群 / `@all`、其他角色或另一个项目。成员变更导致已有接收快照失效时也暂停，管理员核对后显式重试并重新绑定；已经成功发送的通知不会因配置修改自动补发。
- **群可见性**：一个项目使用专用群，首版不把多个项目汇入公共群。群消息对群内所有人可见，@ 不提供访问控制；启用前由管理员确认群成员具有该项目阅读权限。程序无法从项目名册验证 IM 群成员，无法满足这一条件时应选择私信方案。
- **最小内容**：仅含配置的项目显示别名、change ID、Q 编号与答案版本 / 短哈希（或签字 SHA）、需要的角色、通知短编号、时间与“打开平台”链接。默认不含 change 标题、问题 / 答案正文、需求、代码、审查意见、验证输出、内部路径或原始业务事件载荷；首版没有“外发全文”开关。文本和成员引用按渠道分别转义，不能把用户文本变成额外 @ 或链接。
- **深链接**：管理员配置固定的外部 HTTPS 地址和部署前缀；多项目链接为 `/p/<id>/#/changes/<change>/analysis/<Q>` 或 `/p/<id>/#/changes/<change>`，单项目保留原路由。逐段编码 ID，不采信 HTTP Host 或 agent 给出的 URL。链接没有令牌、Cookie、免登录票据；GET 不写状态，登录后仍在当前项目校验身份与角色。旧消息打开的是最新状态，问题确认仍受 T4.2 的 rev + answerHash 保护。签字沿用现有针对操作时 HEAD 的规则，本任务不新增签字版本契约。

示例内容（不含真实接收人）：

```text
[项目 alpha] import / Q-3 第 2 版待 product 确认
通知 n-7ab31 · 请打开平台核对当前答案：<问题深链接>

[项目 alpha] import / commit a1b2c3d 待 dev 签字
验证和独立审查已通过；请打开平台复核当前状态：<变更深链接>
```

## 4. 去重、持久化与发送过程

### 4.1 通知键与事实来源

问题通知键由 `(项目/仓库绑定, changeId, questionId, rev, answerHash, 缺少角色, 通知规则版本)` 规范化后哈希；签字通知键使用 `(项目/仓库绑定, changeId, 完整HEAD SHA, dev, 通知规则版本)`。两类带不同 kind，不能只用事件序号、文本哈希、时间或短 SHA 去重。规则版本是受控协议版本，升级代码时不随意递增并触发群发。

**使用现有哈希链保存通知意图和结果**：`notification.*` 事件通过引擎的 Store 封装调用 `Store.mutate(changeId, …, s => s, …)` 追加，业务状态保持不变；从这些事件还原待发 / 尝试 / 结果投影。投影缓存可以删除重建，SQLite / Postgres 查询索引不承担发送账本权威，不额外直写 `.specforge/changes/*` 文件。

优点是复用跨进程锁、中断保护与审计，不引入文件 / 队列数据库的双写事务；代价是发送尝试也增加事件、触发索引同步和现有状态文件写入。首版小团队可接受该开销，后续若拆分持久队列需单独设计一致性，不能只把发送记录放进可重建索引。

事件记录 key、kind、对象与版本绑定、观察时的源链位置 / HEAD、路由 ID、接收快照指纹、尝试号、结果类别及时间；不复制业务正文、IM 原始响应、Webhook、签名、访问令牌或原始 IM 成员标识。来源位置只是追溯依据，不代替发送前的当前事实校验。

### 4.2 执行顺序

1. 仅已启用项目启动后台 worker；启动时及运行期间重算**当前仍需处理**的事项，不重放已解决的历史事件。首次启用会补当前待办各一次；CLI 在 server 停止期间形成的待办也可在重启后补齐，短暂出现又已解决的待办不补发。
2. 业务事件、名册变化唤醒重算，并以建议 5 秒周期检查 HEAD / 当前就绪条件，覆盖没有新增业务事件的 Git 变化。无积压且仓库空闲、凭据有效时，需求形成后 10 秒内开始首次尝试；锁忙或长任务期间顺延，不宣称实时送达。
3. 在仓库锁内校验项目、链、名册、状态与已存在的 key，幂等登记 queued；发送前再次校验版本、门禁、接收快照和当前配置，记录 started。引擎内部身份仅能执行这套通知操作，不给模型新增发送、签字或状态推进工具。
4. 释放仓库锁后才调用 IM，网络超时建议 10 秒。每项目最多一个发送请求，发送间隔至少 2 秒，定时 tick 不重叠；A 的网络请求不占 B 的仓库锁。首版仍只有一个服务实例，不建设分布式 worker。
5. 将真实传输结果通过 Store.mutate 记回链；锁忙时有界退避等待记录，不重新发网络请求。结果未落盘就退出时按 unknown 处理。`notification.*` 不触发新的业务通知，不自动改变门禁、问题、审批或流程阶段；投影状态没有变化的重复扫描不追加同样的通知事件。

业务请求沿用现有提交路径，不等待通知排队或网络结果。通知失败不撤销已经成功的业务操作，也不靠重放确认 / 签字修复通知。队列持久化遇到现有 pending / 一致性保护时照常暂停，按 [写入恢复](write-recovery.md) 处理，不能为发送提醒绕过 Store 保护。

### 4.3 结果、重试与关闭

| 结果 | 含义与动作 |
|---|---|
| accepted | IM 按所选平台契约明确接受；终止自动重试。仅代表接口受理，不代表成员收到、读过或确认了业务 |
| retry_wait | 平台明确拒绝受理且可重试，例如已核实语义的限流；每轮最多共 5 次尝试，建议间隔 10 / 30 / 120 / 600 秒，叠加抖动，遵守合法 Retry-After 且不早于本地退避；等待期间不持仓库锁 |
| blocked / failed | 配置、成员、鉴权、签名、不可重试参数错误，或尝试耗尽；停止自动重试，管理员修复并写原因后才重试 |
| unknown | 超时、请求发出后断线、无可靠受理语义的 5xx，或 started 后进程退出；可能已送达，默认不自动重发，不声称 exactly-once |
| cancelled | 版本、角色需求或签字就绪条件已失效；发送前停止旧尝试。若同一签字键重新就绪且未 accepted / unknown、未因失败 / 配置暂停，可复用原记录和剩余预算；不能清零失败预算循环发送 |

传输故障只有能证明“尚未发出请求”时才可安全重试；平台明确未受理的响应按上表处理，不能将所有网络错误或 5xx 都当作未送达。成功必须同时符合 HTTP 与所选渠道的业务返回契约，不能仅凭 HTTP 200 记 accepted。

重启先从事件恢复投影；遗留 started 归为 unknown，未尝试的 queued 和可安全重试项继续。首次启用 / 重启补当前待办、索引重建、SQLite ↔ Postgres 切换均使用同一通知键；有 accepted 记录就不再发送。停用通知后停止新请求，已在途请求只完成结果记录；恢复启用时沿用账本。

首次启用必须在预览中展示当前待办数量，管理员确认配置后再启用。改渠道 / 目标群后不自动向新群复制历史；未完成项的路由快照变更需管理员确认。源链、名册、仓库绑定或恢复状态异常时暂停该项目通知；健康项目继续。不以删除日志、重建索引或 `log ack` 清空发送记录来“重试”。去重继承 T4.4 的锚定与可信备份边界，不能保证未锚定发送记录被整体改写或丢失后仍能识别旧发送。

发送前校验后仍可能发生并发确认、停用或 Git 变化；网络请求一旦发出无法保证撤回。消息只陈述尝试时观察到的待办，平台内始终按最新事实校验，不能把旧提醒作为确认或签字证据。

## 5. 配置、运维与首版排除项

服务端显式通知配置包含稳定项目绑定、启用开关、选定 provider、逻辑路由 ID、外部访问基址、允许接收的项目用户名与 IM 成员映射，以及 `webhookEnv` / 必要的 `signingSecretEnv` 等环境变量名。Webhook URL 自身按凭据处理，只从环境读取；签名能力按所选渠道契约校验。配置不提供通用任意 URL 转发器；生产发送仅接受所选渠道受支持的 HTTPS 端点，拒绝重定向，测试通过注入传输实现。

配置仅由可信服务端管理员维护，不开放 HTTP 修改群或凭据、agent 修改接收人、把客户端传入的回调地址作为目的地。无配置时不读取 IM 凭据、不新增通知事件、不建立外连；显式配置错误只令对应项目通知 blocked，不能悄悄发送到默认项目或使其他项目业务不可用。日志 / 错误不输出环境变量值、请求头、签名、完整 URL 或原始响应。

首版已提供本地管理入口（完整参数见 [通知说明](im-notifications.md)）：

- `sf notify preview`：只读展示当前候选、角色、路由和渲染后的最小内容，无消息发送和业务修改。
- `sf notify status`：按项目 / change 列出通知短编号、状态、尝试次数、下次时间与脱敏错误；关闭、blocked、未知结果均可区分。
- `sf notify retry … --reason …`：项目内有效管理员显式申请一轮新的有界尝试预算，重新校验当前资格与接收映射并保留累计次数和全部历史。unknown 另需明确接受重复消息风险；已 accepted 不提供重发功能。普通 dev / product 和 agent 不能通过该入口操作发送记录。

发送账本在现有事件时间线可追溯；首版不另做通知中心、管理页面或监控平台。排除定时催办、每日摘要、工作时段 / 个人偏好、多渠道降级、群回执 / 阅读确认、IM 内确认 / 签字按钮、消息回调、免登录链接，以及待回答、审批 spec/design、评论、任务接管、故障与升级告警。没有引入模型调用或消息生成模型。

## 6. 验收标准

以下是整个 T4.5 的目标；判定、账本、注入传输、管理入口与浏览器证据见第 8～10 节。AC-12 的真实群发送及成员 @ 效果仍待指定测试群与明确发送授权。

| 编号 | 可观察结果 |
|---|---|
| T45-AC-01 | open / rejected 不发待确认提醒；drafted 只发缺少的人类角色。覆盖回答者自动确认、同角色一人确认结束需求、同文新修订、同修订追加角色、确认 / 推迟 / 作废 / delivered 取消 |
| T45-AC-02 | closing 但上游、G6A 或独立审查不通过时不催签；全部就绪且当前 SHA 没有人类签字才提醒 dev。覆盖当前 SHA 的 human pass / fail、旧 SHA 签字、新 HEAD、打回 / 升级后修复、同 SHA 就绪恢复和 S / M / L 差异 |
| T45-AC-03 | 配置成员与名册按项目和角色取交集，停用 / 移除角色 / 快照变化在发送前生效；无有效映射不全群广播；A / B 同名数据、凭据、接收人和结果不串用 |
| T45-AC-04 | 重复 tick / 并发登记只创建一个 key；重启、CLI 离线形成待办、首次启用、索引重建及后端切换都只补当前需求，accepted 不重发，notification 事件不产生通知循环 |

`packages/store/src/notifications.ts` 导出引擎内部 `NotificationLedger`，构造参数为稳定 `projectId`、默认关闭的 `enabled`、内存路由及可注入时钟。路由包含 `id`、`provider: feishu`、目的地 `revision` 和显式用户名 / 成员 ID 映射；换群必须修改 revision。原始成员 ID 只在内存中交给后续传输层，事件仅保存接收快照指纹。

| 内部方法 | 当前行为 |
|---|---|
| `list()` | 在仓库锁内校验当前项目并只读还原发送投影 |
| `reconcile()` | 启用时重算当前需求，登记 queued / blocked，取消过时需求；重复调用不追加相同事件 |
| `prepare(key)` | 锁内复核版本、就绪条件、名册及路由指纹，登记 started；同项目已有 started 时不再登记，返回后仓库锁已释放 |
| `finish(key, attempt, result)` | 校验尝试号并记录已分类结果；即使关闭也可完成在途记账，重复 accepted 幂等，不接收原始传输响应 |
| `recoverInterrupted()` | 将遗留 started 保守记为 unknown；只能在确认前一个 worker 已退出后的独占启动阶段调用 |

所有写入均经 `Store.mutate`，业务状态字节、HEAD、已有门禁绑定及可信锚定保持。每次写入前校验当前配置、链、状态、名册和仓库绑定；损坏不能靠通知事件覆盖。初始及每轮最多 5 次自动尝试，retry_wait 保留到期时间与尝试预算，accepted / unknown 不自动重发，blocked / failed 不自动恢复。d 已通过可选 retry 元数据和 notification.retried 事件扩展显式管理员重试，保留累计尝试及全部历史，见第 10 节。

## 9. T4.5c 已交付范围

服务支持独立的 `--notifications <JSON>`；多项目按登记 ID 匹配，单项目要求恰好一个稳定 ID，并与显式 Postgres 索引 ID 一致。默认关闭，逐项目配置错误记 blocked / configuration；不存在默认项目或任意 HTTP 目的地回退。首版要求签名密钥和 Webhook 均只从环境读取，限制飞书官方 HTTPS hook，拒绝重定向；成员统一使用显式 Open ID。完整配置与恢复步骤见 [通知说明](im-notifications.md)。配置文件修改需重启，不提供 HTTP 配置入口或 agent 发送工具。

后台启动和业务事件唤醒扫描，每 5 秒额外检查 HEAD / 当前事实；每项目一项在途请求，开始至少间隔 2 秒，网络 10 秒超时。`packages/runner/src/notification-owner.ts` 用独立通知 owner 保存 PID / token，在短期仓库锁内取得或接替确定死亡的进程；活 owner 或未知 owner 均不抢占。只有新 owner 启动阶段才调用 recoverInterrupted，因此不会把另一个活 worker 的在途请求记为 unknown。owner 本身不占业务锁，网络和结果落盘等待均在锁外。
